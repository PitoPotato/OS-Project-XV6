CS333 Lab 2 – System Calls
Task 3.1 – Using GDB

Q1. Which function called syscall?
Answer: usertrap() called syscall(), as shown by frame #1 immediately
below syscall() in the backtrace.

    Evidence (gdb-normal.png):
    (gdb) backtrace
    #0  syscall () at kernel/syscall.c:161
    #1  0x0000000080001b3a in usertrap () at kernel/trap.c:68
    #2  0x0000003ffffff09c in ?? ()

Q2. What is p->trapframe->a7 and what does it represent?
Answer: p->trapframe->a7 is 0xf (15 in decimal), which is SYS_open in
kernel/syscall.h. The a7 register holds the system call number, so the
process is requesting open(). In this version of xv6, init's first
user-space system call is open("console", O_RDWR) in user/init.c.

    Evidence (gdb-normal.png):
    (gdb) p /x p->trapframe->a7
    $2 = 0xf

Q3. What was the previous CPU mode?
Answer: The previous mode was User mode. The observed sstatus value is
0x200000022. Its SPP bit (bit 8, Supervisor Previous Privilege) is 0,
which indicates that the trap came from User mode into Supervisor mode.

    Evidence (gdb-normal.png):
    (gdb) p /x $sstatus
    $3 = 0x200000022

Q4. Which assembly instruction panics? Which register is num?
Answer: The faulting instruction is lw a3,0(zero) at 0x80001d8a
(syscall+16), corresponding to num = *(int *)0; at kernel/syscall.c:161
in the deliberately faulty build. It attempts to load a 32-bit value
from address 0 into a3. Thus, a3 is the destination register allocated
for num; the load faults before it can complete.

    Evidence (gdb-panic.png):
    (gdb) x/i $pc
    => 0x80001d8a <syscall+16>:
       lw a3,0(zero) # 0x0

Q5. Why does the kernel crash?
Answer: The deliberately inserted statement num = *(int *)0; reads
address 0, which is not mapped in the kernel's virtual address space.
The access causes a load page fault: scause = 0xd (13) identifies the
exception, stval = 0x0 identifies the faulting virtual address, and
sepc = 0x80001d8a identifies the faulting instruction. kerneltrap()
cannot handle this exception and calls panic("kerneltrap").

    Evidence (gdb-panic.png, QEMU output):
    scause=0xd sepc=0x80001d8a stval=0x0
    panic: kerneltrap

Q6. Which process was running? What is its PID?
Answer: The process was init, with PID 1. GDB was stopped in syscall()
at kernel/syscall.c:161, immediately before the faulting instruction,
when the process name and PID were inspected.

    Evidence (gdb-panic.png):
    (gdb) p p->name
    $1 = "init", '\000' <repeats 11 times>
    (gdb) p p->pid
    $2 = 1

After collecting the panic evidence, num = p->trapframe->a7; was restored
in kernel/syscall.c.
